[Model Context Protocol](https://modelcontextprotocol.io) server integration
for Yii3 over the **official** [`mcp/sdk`](https://packagist.org/packages/mcp/sdk)
(PHP Foundation + Symfony): expose your application's domain operations as MCP
tools/resources for AI agents (Claude Code, Claude Desktop, …) through a
PSR-15 Streamable HTTP endpoint, with tools resolved through the Yii3 DI
container.

The runtime itself lives in [`rasuvaeff/mcp`](https://github.com/rasuvaeff/mcp) and knows nothing about
Yii; the OpenAPI bridge is in [`rasuvaeff/mcp-openapi`](https://github.com/rasuvaeff/mcp-openapi). This package
adds the Yii3 side: `config-plugin` wiring, params and `mcp:doctor`. Upgrading from 5.x:
[UPGRADE.md](UPGRADE.md).

> **Using an AI coding assistant?** [llms.txt](llms.txt) contains a compact
> API reference you can share with the model. Contributors: see [AGENTS.md](AGENTS.md).
> Projects using the [llm/skills](https://github.com/roxblnfk/skills) Composer
> plugin also get this package's agent skill synced into `.agents/skills/`
> automatically on install.

## Requirements

| Requirement | Version |
|-------------|---------|
| PHP | 8.3 – 8.6 |
| `mcp/sdk` | `~0.10.0` (experimental until 1.0 — hence the tilde pin) |
| `rasuvaeff/mcp`, `rasuvaeff/mcp-openapi` | `^0.1` (installed automatically) |
| `firebase/php-jwt` | optional, `^7.0`: JWT validation for the OAuth resource server |
| MCP protocol | 2024-11-05 … 2025-11-25 over `initialize` (negotiated), 2026-07-28 stateless |
| `ext-fileinfo` | required by the SDK |

## Installation

```bash
composer require rasuvaeff/yii3-mcp
```

## Usage

### 1. Declare a tool

Tools are ordinary Yii3 services. Capability methods are annotated with the
SDK's own attributes — this package invents no protocol structures:

```php
use Mcp\Server\Capability\Attribute\McpTool;

final readonly class OrderTools
{
    public function __construct(private OrderRepository $orders) {}

    /**
     * Returns the current status of an order.
     */
    #[McpTool(name: 'order.status')]
    public function status(string $orderId): string
    {
        return $this->orders->get($orderId)->status->value;
    }
}
```

Input schemas are generated by the SDK from the method signature and DocBlock.
`#[McpResource]`, `#[McpResourceTemplate]` and `#[McpPrompt]` methods work the
same way — all four SDK capability attributes are recognized.

### 2. Register it

```php
// config/params.php
return [
    'rasuvaeff/yii3-mcp' => [
        'server_name' => 'my-app',
        'server_version' => '1.0.0',
        'tools' => [OrderTools::class],
        'endpoint_secret' => getenv('MCP_SECRET'),
    ],
];
```

Handlers are registered as `[class, method]` references — the SDK resolves the
instance through the Yii3 container on call, so constructor dependencies are
injected the normal way.

### 3. Route the endpoint

```php
// config/routes.php
Route::methods(['POST', 'GET', 'DELETE', 'OPTIONS'], '/mcp')
    ->middleware(SharedSecretMiddleware::class)
    ->action(McpAction::class),
```

An MCP client connects with the secret header:

```json
{
    "mcpServers": {
        "my-app": {
            "type": "http",
            "url": "https://example.com/mcp",
            "headers": { "X-Mcp-Secret": "..." }
        }
    }
}
```

Clients that authenticate with OAuth 2.1 instead route
`BearerTokenMiddleware` in front of the action — see
[OAuth 2.1 resource server](https://rasuvaeff.github.io/mcp/oauth).

### stdio for local development

```bash
./yii mcp:serve
```

Claude Code config: `claude mcp add my-app -- ./yii mcp:serve`.

The `mcp:serve`, `mcp:list` and `mcp:doctor` commands are registered through
the package's `yiisoft/yii-console` params, so they show up in `./yii list`
right after `composer require` — no application-side configuration. An
application that maintains its own commands map merges with it recursively
(the application layer wins on a name conflict, so a command can be renamed
or rebound by re-declaring its name); an application not using
`yiisoft/config` can still list the three classes in its console params the
way previous versions documented it.

### Check what is served

```bash
./yii mcp:list             # every tool, resource and prompt, without a client
./yii mcp:doctor           # configuration health check with stable exit codes
```

`mcp:doctor` is `McpDoctorCommand` over `Doctor\McpDoctor`, which returns a
`DoctorReport` of `CheckResult`s (`CheckStatus`, `CheckCategory`). See
[Operations](https://rasuvaeff.github.io/mcp/operations).

## Security

- **The endpoint is trusted-only.** MCP tools execute application code;
  treat the endpoint like an admin API. Ship it behind
  `SharedSecretMiddleware` or `OAuth\BearerTokenMiddleware` (an empty secret rejects every request with an
  explanatory 503) or an explicit network ACL.
- Tool errors are returned as MCP error envelopes by the SDK — internals are
  not leaked as 500 traces.
- The core registers **no tools by default**; every exposed operation is an
  explicit entry in `params['rasuvaeff/yii3-mcp']['tools']`.
- **Sessions are bound to the client that created them** (immutable owner
  stamped at `initialize`, verified before every POST/DELETE, and the SDK's own
  principal binding behind it): a leaked `Mcp-Session-Id` alone does not let
  another authenticated client act in — or destroy — a foreign session. Session files are owner-only (`0700` dir,
  `0600` files) in an application-specific directory.
- **Capability names are unique across the whole server, enforced.** A
  collision between any registration paths (attribute tools, configurators,
  the OpenAPI bridge) fails the build with
  `DuplicateCapabilityException` — never the SDK's silent last-write-wins,
  which would leave visibility/cache/RBAC/audit rules describing a vanished
  handler.
- All caller-influenced output is size-bounded **before** allocation:
  upstream response bodies (`openapi.max_response_bytes`, incremental read),
  spec documents (10 MiB + `$ref` depth/node budget) and tool results
  (`limits.tool_result_bytes`).
- **OAuth 2.1** through `OAuth\BearerTokenMiddleware` (the SDK's resource
  server pieces): token, audience, issuer and scopes are checked before the
  transport runs; see [OAuth 2.1 resource server](https://rasuvaeff.github.io/mcp/oauth).
- Nested tool arguments are masked at every depth, objects included
  (`ArgumentMasker`), and a multi round-trip `requestState` is bound to its
  request and client.
